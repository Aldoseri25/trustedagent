Architecture snapshot

1 · IdentityEach agent holds a P-256 key; its identifier is a did:key built from the public key (multicodec 0x1200). No registry needed to know who signed.
2 · ClaimsW3C-VC-style credentials: issuer, subject, type, claim, expiry, proof. Types: VerifiedVendor (registry), Delegation (human → agent, with scope and cap), signed action receipts.
3 · VerificationFresh-nonce challenge (possession) → credential signature → trusted issuer → expiry → signed revocation list → hash-chained history check.
4 · PolicyVerifier-owned rules turn evidence into ACCEPT, REFUSE or ESCALATE. No score: every decision cites the checks that produced it.

Trust is granted by issuing a signed credential, scoped by narrowing its claim (the cap slider), and revoked by the registry publishing a signed revocation list.

Failure test. Mallory tries three things: replaying Meridian’s real credential (fails possession proof: she cannot sign the nonce), issuing herself a credential (fails trusted-issuer check), and editing a copy of Meridian’s credential (fails signature check). Each fails at a different layer, so the defence is not a single point.

Two-year thesis · agent identity and reputation

By 2028 most commerce between organisations will be negotiated by software acting for people. Three things must exist or it collapses into spam and fraud: identity an agent can prove, authority that is scoped and revocable, and a record others can verify without asking the agent’s owner.

Identity will be cryptographic and cheap. Every agent holds a key and a DID; names, logos and model brands will mean nothing. Possession of a key means everything, so every interaction opens with a challenge.

Authority will flow as delegation chains (human → organisation → agent → sub-agent), each hop a signed credential that can only narrow scope: amount, time, counterparty, action. Verifiers check the chain, not a profile page. Revocation must be as fast as issuance, because an agent doing 10,000 tasks a day can do 10,000 wrong things before anyone reads an email.

Reputation will stop being a number. A score is a rumour; signed receipts counter-signed by counterparties and anchored in hash-chained logs are evidence. Each verifier applies its own policy to the same evidence, so a payments agent and a research agent can trust one vendor differently.

The hard problems are sybils and issuers. Fresh keys are free, so new agents start with zero authority and earn it through human-backed delegations and vouches that put the voucher’s own standing at stake. Trust anchors will be plural and competing, like certificate authorities, with transparency logs to expose bad issuers.

Whoever standardises the claims vocabulary, the revocation path and the policy language, built on DIDs and Verifiable Credentials, becomes the TLS of the agent economy.

Notes

Built with: Claude for design and code; WebCrypto (ECDSA P-256, SHA-256); no libraries, one file.

Key decisions: real signatures over canonical JSON; possession challenge so stolen credentials are useless; verifier-side policy instead of a global score; hash-chained signed action log as reputation evidence; extends did:key and the VC data model (simplified, not JSON-LD or Data Integrity proofs).

Out of scope: DID resolution beyond an in-page key cache, network transport between agents, sybil resistance at scale, privacy-preserving (selective disclosure) credentials, persistent storage. All keys are regenerated on each page load.
